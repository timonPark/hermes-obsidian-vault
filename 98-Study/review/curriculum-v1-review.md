# 헤르메스 & 옵시디언 학습 커리큘럼 검토 보고서

검토일: 2026-10-06  
검토 대상: [`curriculum-v1.md`](../curriculum/archive/curriculum-v1.md) (v1)

## 1. 종합 의견

현재 커리큘럼은 전체 흐름이 잘 설계되어 있습니다. 특히 다음 순서가 자연스럽습니다.

> 옵시디언 기초 → 헤르메스 기초 → 두 도구의 연결 → 작은 자동화 → 업무 적용 → 운영

또한 다음 원칙이 일관되게 반영되어 있어 실무 교육용으로 적합합니다.

- 옵시디언을 먼저 익힌 뒤 헤르메스를 학습하도록 구성함
- 전용 폴더와 최소 권한으로 시작함
- 자동화 결과를 사람이 최종 검토하도록 함
- 보안, API 키, 외부 모델 전송 위험을 다룸
- 학습 결과물을 실제 노트와 업무 워크플로로 남기도록 함

다만 현재 문서는 정상적으로 작동하는 상황을 중심으로 구성되어 있습니다. 실제 교육에 사용하기 전에는 헤르메스의 실제 기능 확인, 자동화 실패와 복구, AI 결과 검증, 백업과 동기화의 구분을 보완하는 것이 좋습니다.

## 2. 가장 먼저 보완할 사항

### 2.1 헤르메스 기능과 용어 확인

현재 커리큘럼에는 다음 기능이 지원된다는 전제가 포함되어 있습니다.

- `~/.hermes` 폴더
- CLI 또는 데스크톱 앱
- 모델 연결
- 메모리와 스킬
- 프로필
- 게이트웨이와 메신저 연동
- cron 기반 스케줄
- 옵시디언 플러그인 연동

헤르메스의 배포판과 버전에 따라 명칭이나 지원 방식이 달라질 수 있으므로, 교육 전에 실제 환경을 확인해야 합니다.

| 항목 | 실제 지원 여부 | 공식 명칭 | 설정 위치 |
|---|---|---|---|
| 설치 방식 |  |  |  |
| 모델 연결 |  |  |  |
| 메모리 |  |  |  |
| 스킬 |  |  |  |
| 파일 접근 권한 |  |  |  |
| 메신저 연동 |  |  |  |
| 예약 실행 |  |  |  |
| 옵시디언 연동 |  |  |  |

이 표를 채운 뒤 실제 지원되지 않는 기능은 삭제하거나 대체 실습으로 바꾸는 것이 안전합니다.

### 2.2 백업과 동기화 구분

5회차의 Git 실습은 유용하지만, Git·동기화·백업은 서로 다른 목적을 가집니다.

| 개념 | 목적 |
|---|---|
| Git | 변경 이력 확인, 비교, 복구 |
| 클라우드 동기화 | 여러 기기 간 파일 동기화 |
| 백업 | 원본 손상 시 별도 사본으로 복구 |

다음 항목을 5회차에 추가하는 것을 권장합니다.

- `.gitignore` 작성
- API 키와 개인정보가 Git에 들어가지 않도록 점검
- 자동화 실행 전후 `diff` 확인
- 잘못 수정된 노트 복구
- 첨부파일과 대용량 파일 관리
- Git만으로는 백업이 완성되지 않는다는 점 설명

### 2.3 옵시디언 검색과 첨부파일 관리

현재 옵시디언 기초 내용에 다음 항목을 추가하면 14회차의 지식 검색으로 자연스럽게 연결됩니다.

- 검색 문법: `path:`, `tag:`, 제외 조건, 날짜 조건
- 블록 링크와 임베드
- 첨부파일 저장 위치와 파일명 규칙
- 속성의 타입: 날짜, 목록, 체크박스
- 노트 이름 변경 시 링크 업데이트
- 템플릿 변수
- 기본 쿼리 또는 Dataview 계열 도구의 역할과 한계

## 3. 자동화 운영 관점의 보완

### 3.1 실패와 복구 실습 추가

현재 커리큘럼은 자동화가 정상적으로 동작하는 흐름에 집중되어 있습니다. 실무에서는 실패를 발견하고 복구하는 능력이 더 중요할 수 있으므로 다음 실습을 추가하는 것이 좋습니다.

- 잘못된 폴더에 파일이 생성된 경우
- 기존 노트를 덮어쓴 경우
- 중복 노트가 만들어진 경우
- 링크가 깨진 경우
- 모델이 사실과 다른 요약을 만든 경우
- 스케줄이 중복 실행된 경우
- API 한도 초과 또는 연결 실패
- 자동화 중단, 재실행, 이전 상태 복구

모든 자동화는 다음 구조로 설계하도록 지도하면 좋습니다.

> 입력 → 처리 → 승인 → 반영 → 실패 시 복구

### 3.2 AI 결과 검증과 출처 관리

14회차와 15회차에 다음 원칙을 명시적으로 추가할 것을 권장합니다.

- 요약 결과를 원문과 대조하기
- 사실과 모델의 추론을 구분하기
- 답변에 출처 노트 링크 포함하기
- 출처가 없으면 확인할 수 없다고 답하게 하기
- 회의록의 발언자, 결정 사항, 담당자를 원문과 대조하기
- 자동 생성 문서를 바로 확정하거나 외부에 발송하지 않기

## 4. 회차별 개선 의견

### 4.1 6회차의 학습량 조정

6회차에는 터미널, LLM, 에이전트, API 키, 과금, 보안이 모두 들어 있어 초보자에게 부담이 될 수 있습니다.

가능한 조정안은 다음과 같습니다.

- 6회차: 터미널과 파일 경로
- 7회차: LLM·에이전트·도구·메모리 개념
- 8회차: 헤르메스 설치와 모델 연결

회차 수를 유지한다면 6회차에서는 터미널 실습을 중심으로 하고, AI 개념은 7회차 시작에 짧게 다루는 방법이 좋습니다.

### 4.2 11회차의 기간 명확화

“일주일 동안 자동화를 돌리고 문제점을 기록한다”는 내용은 수업 중 실습이 아니라 회차 사이 과제로 구분해야 합니다.

권장 형식:

- 수업 중: 인박스 자동화 구축 및 테스트 데이터 3건 실행
- 회차 사이 과제: 실제 메모로 5~7일 사용
- 다음 회차 시작: 실패 사례와 수정 사항 리뷰

### 4.3 16회차의 일정 조정

“2주 이상 실제로 사용한 결과를 공유한다”는 졸업 조건은 4~5주 전체 일정 안에서 다소 빡빡할 수 있습니다.

다음 중 하나를 선택하는 것이 좋습니다.

- 졸업 과제를 14회차부터 시작하기
- 정규 교육을 마친 뒤 2주 운영 기간을 별도로 두기
- 16회차에서는 1주 사용 결과를 공유하고, 2주차 결과는 후속 리뷰로 진행하기

## 5. 보안과 개인정보 항목 보완

15회차의 보안 체크리스트를 다음처럼 구체화하면 실무 적용성이 높아집니다.

### 정보 분류

- 공개 정보
- 사내 일반 정보
- 내부 제한 정보
- 개인정보
- 고객·영업·보안 기밀

### 확인할 내용

- 어떤 정보가 외부 모델로 전송되는가
- 모델 제공자가 데이터를 학습에 사용하는가
- API 키를 어디에 저장하는가
- 노트, 프롬프트, Git 이력에 비밀정보가 남지 않는가
- 메신저 연동 시 대화 내용이 어디에 저장되는가
- 자동 생성 결과가 외부로 발송되기 전에 사람이 승인하는가

API 키는 노트, 프롬프트, 채팅, Git 저장소에 저장하지 않고 환경 변수나 조직에서 승인한 비밀 저장소를 사용하도록 안내해야 합니다.

## 6. 역할 문서와 커리큘럼의 일치 여부

역할 정의 문서에는 다음 업무가 예시로 제시되어 있습니다.

- 회의록·음성 메모 처리
- 기술 문서, ADR, 장애 회고
- 볼트 기반 질의
- 일일 요약과 주간 리포트

현재 커리큘럼은 회의록, 기술 문서, 지식 검색, 리포트는 다루지만 음성 메모와 첨부파일 처리는 직접 다루지 않습니다.

실제 활용 사례로 음성 메모를 중요하게 생각한다면 12회차 또는 14회차에 다음 실습을 추가하는 것이 좋습니다.

- 음성 메모 → 텍스트 → 회의록
- PDF·이미지·코드 파일 → 옵시디언 노트
- 첨부파일 저장 위치와 이름 규칙
- 음성·문서의 외부 모델 전송 주의점

## 7. 완료 기준을 측정 가능하게 바꾸기

현재 완료 기준은 방향은 좋지만 일부는 주관적으로 판단될 수 있습니다. 다음과 같이 행동 기준으로 바꾸면 평가가 쉬워집니다.

- 옵시디언 검색 문법을 사용해 질문 5개를 직접 수행한다.
- 속성 4개가 포함된 템플릿으로 노트 3개를 만든다.
- 잘못 수정된 파일을 Git으로 복구한다.
- 헤르메스가 허용 폴더 밖에 쓰지 못하는 것을 테스트한다.
- 회의록 자동화 결과를 원문과 대조해 오류를 기록한다.
- 자동화 중단·재실행·복구를 각각 한 번씩 수행한다.
- 자동 생성 답변에 출처 링크가 포함되는지 확인한다.

## 8. 권장 수정 우선순위

### 반드시 반영

1. 헤르메스 실제 기능과 용어 확인
2. 자동화 실패·검증·복구 실습 추가
3. Git·백업·동기화 구분
4. 개인정보·기밀정보 분류와 API 키 관리

### 가능하면 반영

6. 음성 메모 처리
7. 완료 기준의 측정 가능성 강화
8. 수업 중 실습과 회차 사이 과제 구분

## 9. 최종 결론

현재 커리큘럼은 교육의 뼈대가 충분히 좋으며, 큰 구조를 다시 설계할 필요는 없습니다.

가장 중요한 보완점은 정상 작동하는 워크플로를 만드는 것에서 끝나지 않고, 다음까지 훈련하도록 만드는 것입니다.

> 자동화가 틀렸을 때 발견하고, 검증하고, 중단하고, 되돌리는 방법

위 내용을 반영하면 초보자용 입문 과정이면서도 실제 팀 업무에 적용 가능한 운영 교육으로 발전할 수 있습니다.
