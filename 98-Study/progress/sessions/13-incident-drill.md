## 2. 배운 것
- 장애 대응 4단계: **발견 → 중단 → 복구 → 재발 방지**
- 오늘(2026-10-06) 실제로 겪은 장애 7건

  | # | 장애 | 발견 | 중단·복구 | 재발 방지 |
  |---|---|---|---|---|
  | 1 | 1년짜리 Claude 로그인 토큰을 대화창에 붙여넣음 | 팀장이 대화에서 발견 | 토큰 폐기 안내 | API 키 원칙 3번 "말로 전하지 않는다" |
  | 2 | 팀장의 `git status`가 `.git/index.lock`을 남김 | 볼트 점검 중 경고 | 학습자가 `rm` | 상태 확인은 `--no-optional-locks`로만 |
  | 3 | 설계 문서 끝에 엉뚱한 한 줄이 붙음 | `git status`의 `M` 표시 | 줄 삭제 | 수동 편집 후 `git diff` 확인 |
  | 4 | "매시간 정각"이 "60분마다"로 등록됨 | 정각에 알림이 안 옴 → `cron list` | 원인 확인 후 삭제 | 시각이 중요하면 크론 표현식 직접 지정 |
  | 5 | 수동 실행으로 스케줄이 17:06으로 밀림 | `cron list`의 Next run | — | 간격형 일정의 특성 이해 |
  | 6 | 검토하면서 무관한 노트 2건에 `project: [[고객미팅]]` 입력 | 팀장이 속성 대조 | 학습자가 수정 | 승인 단계에서도 원문 대조 |
  | 7 | 쓰기가 막히자 헤르메스가 "보안 설정을 해제하라"고 제안 | 슬랙 답장 | 따르지 않음 | 권한 확대는 사람이 판단 |

  | 8 | **17:20 데일리 요약이 "오늘 기록이 없습니다"라고 보고** (실제로는 `10-Notes` 4건 + `90-Hermes` 1건) | 정답(4~5건)과 비교 | 조사: `cron runs`(completed만 표시) → 거부 로그 없음(가설 1 기각) → 17:20 로그에서 **`tool_turns=0`, `api_calls=1`** 확인 = **파일을 한 번도 읽지 않고 답함** | 지시문 개선만으로는 해결 안 됨 (#9) | 아래 #9와 함께 해결 |

  | 9 | 17:30 개선판이 **정시 실행·completed인데 슬랙에 안 옴** | 로그: 여전히 `tool_turns=0` + **`agent returned [SILENT] — skipping delivery`** | **근본 원인**: 스케줄 작업은 `hermes tools`의 **cron 플랫폼 도구 설정**만 받음 (공식 문서) → 파일 도구가 없었음. 작업에 `enabled_toolsets: ["file"]` 지정 + "[SILENT] 금지" 추가 → `run` 시험 | 17:37 요약이 **정답과 완전히 일치** (5건, 지시3·회의1·메모1, 할 일 3개·기한, 검토 대기 1, 근거 파일 5개) ✅ |

  - #8 교훈: 실행 기록의 `completed`는 "작업이 끝났다"일 뿐 "맞게 했다"가 아님. **도구를 안 쓰고 지어낸 답**도 completed로 찍힘
  - #9 교훈: 설정은 "했다"로 끝나지 않고 **"어디에 적용됐는지"**까지 확인한다 (11회차 도구 설정은 CLI·Slack에만 적용, cron은 별도)
  - 권한은 넓게 열지 않고 **작업 단위로** 준다: cron 전체가 아니라 요약 작업 하나에만 `file` 도구
  - 조사 습관: 증거가 추측과 다르면 추측을 버린다 (가설 "안전장치에 막힘" → 로그로 기각)
  - 7건 중 **헤르메스 자체의 실수는 1건(#4)**. 나머지는 사람(학습자·팀장)의 실수이거나 AI의 위험한 제안
- 중단은 삭제가 아니라 `pause`: 원인을 찾은 뒤 같은 설정으로 다시 켤 수 있음
  - 공통점: 모두 **증거(로그, `git status`, `cron list`, 실제 파일)로 발견**함
